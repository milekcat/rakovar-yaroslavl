## 3. Критические ограничения текущего кода

1. `DEMO_MODE=true` обязателен для безопасной публичной демонстрации. Тестовый checkout не создаёт коммерческий заказ и не уведомляет компанию как рабочий канал.
2. Гостевой browser ID не является подтверждённой личностью. До production нельзя использовать его как единственный ключ лояльности/денег.
3. SQLite и `/tmp` не дают долговременного хранения. Не вносить реальные клиентские данные.
4. Один admin password не заменяет роли сотрудников, MFA и аудит привилегированных действий.
5. Контент-план не публикует посты в соцсети. Статус «интеграция» не означает подключённый provider.
6. MAX Long Polling предназначен для preview. Боевой режим требует webhook, секретов, домена/публичного HTTPS и мониторинга.
7. Каталог и контактные данные — исходные гипотезы. Все сведения должны быть утверждены компанией до публикации.

## 4. Архитектура для «одного согласованного обновления»

«Одно обновление» достижимо только после предварительного сбора внешних зависимостей. До дня переключения должны быть готовы:

- PostgreSQL и проверенные миграции; тест восстановления backup.
- Эквайринг компании: договор/merchant ID, webhook secret, тестовые платежи и возвраты.
- Подтверждённый каталог: SKU, цены, остатки, вес, состав/аллергены, фото и лицензии.
- Логистика: зоны, адреса, тарифы, минимальный заказ, слоты, правила самовывоза.
- MAX bot token, Mini App URL, утверждённый бот и webhook endpoint.
- VK community ID и токен с минимальными scopes; Telegram bot token; разрешённые каналы и владельцы контента.
- Утверждённые правила клуба, рефералов, конкурсов, призов, согласий и обработки персональных данных.
- Ответственные роли, политика возврата, поддержки и SLA.

После этого единый release включает: переключение production config, миграции, включение payment adapter, webhook, реальных уведомлений, publisher workers, роли, monitoring, smoke/e2e tests и rollback plan. Включение только одной переменной окружения не может заменить отсутствующие договоры, API-права и операционные правила.

## 5. Рекомендуемый production stack

- Flask API оставить на первом релизе, не переписывать стек без необходимости.
- PostgreSQL + Alembic migrations — постоянное хранилище.
- Redis/Render Key Value + отдельный worker — очередь публикаций, уведомлений, webhooks и повторов.
- Outbox pattern и idempotency keys для платежей, заказов и начислений.
- Provider interfaces: PaymentProvider, InventoryProvider, DeliveryProvider, CRMProvider, SocialPublisher, NotificationProvider.
- RBAC: owner, admin, manager, warehouse, content_editor, support; MFA для privileged accounts.
- Sentry/эквивалент, structured logs, alerts, health/readiness endpoints.
- Preview, staging и production должны иметь раздельные БД и секреты.

## 6. Приёмочные критерии до реальной работы

- Тестовый заказ проходит от корзины до оплаты, webhook не создаёт дублей.
- Повторный webhook безопасен; refund корректно отменяет заказ, бонусы и резервы.
- Остаток не уходит ниже нуля при конкурентных заказах.
- Реферальный бонус начисляется только один раз после qualifying paid order; self-referral и повторные аккаунты отсеиваются.
- Конкурс хранит снимок правил и список допущенных заявок; протокол выбора победителя неизменяем и выгружаем.
- Администратор видит только разрешённые ему функции; все критические действия попадают в audit log.
- Публикация в соцсети показывает фактический provider post ID/status; ошибки повторяются по политике retry и не создают дубли.
- Backup восстанавливается в отдельную среду; health checks, logs, alerts и rollback проверены.
- Витрина корректно работает на мобильных экранах, keyboard-only, screen reader и при медленной сети.

## 7. Решение по текущему этапу

Текущая сборка — preview/acceptance prototype. Она подходит для демонстрации концепции и сбора требований у команды «Раковаръ». Не использовать её для реальных оплат, заказов, конкурсов или хранения персональных данных. Следующий шаг — разместить полный исходный пакет в корне GitHub, выполнить CI и развернуть отдельный Render preview; production запускать после закрытия внешних зависимостей и приёмки компании.
