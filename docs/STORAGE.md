# Постоянные данные и восстановление

Проверено 9 ноября 2026 года. Этот этап сохраняет Flask, существующие API и
preview-данные. Коммерческий checkout остаётся выключенным. Работа с реальной
базой Render и перенос её данных в этом этапе не выполнялись.

## Выбор хранилища

| Настройка | Результат |
|---|---|
| `DATABASE_URL` отсутствует | SQLite из `SQLITE_DB_PATH` для разработки и временного preview |
| `DATABASE_URL=postgresql://…` или `postgres://…` | PostgreSQL через `psycopg[binary]==3.3.8` |
| PostgreSQL недоступен или URL неподдерживаемого типа | Ошибка; скрытого перехода на SQLite нет |

URL и пароли задаются через защищённые переменные окружения. Они не передаются
параметрами скриптов, не печатаются в отчётах и не добавляются в Git. Параметры
TLS выбираются по документации провайдера; проверку сертификатов отключать
нельзя. Для каждой среды нужны отдельные база, секрет сессии и доступы.

SQLite на локальной файловой системе Render free теряет данные при перезапуске,
пересборке или засыпании. Отдельный PostgreSQL решает эту проблему хранения,
но бесплатная база Render имеет собственный ограниченный срок жизни. Не
использовать её как постоянную коммерческую инфраструктуру без отдельного
решения по эксплуатации.

Драйвер выбран для сохранения существующего Python-стека. Пакет имеет лицензию
LGPL; это зависимость проекта, её лицензию и комплект поставки нужно учитывать
при распространении. Здесь проверена версия 3.3.8, а не заявлена совместимость
с любым будущим выпуском драйвера.

## Транзакции и совместимость

`storage.connect_database()` открывает одно соединение на единицу работы.
Выход без исключения фиксирует транзакцию, исключение откатывает её целиком.
SQLite начинает `BEGIN IMMEDIATE`; PostgreSQL использует advisory transaction
lock для старых операций read/modify/write. Приложение и бот проходят через
один слой, поэтому проверка лимита и изменение данных не расходятся между
процессами.

Это переходное решение с общей блокировкой. Оно сохраняет корректность
legacy-потоков, но ограничивает параллелизм. Его нельзя называть архитектурой
для высокой нагрузки. Следующий шаг после выделения сервисов заказа, склада и
лояльности — точечные блокировки строк, условные обновления и пул соединений
с нагрузочной проверкой.

Внутри открытого контекста запрещён второй `connect_db()` для этого же потока:
он будет ждать собственную блокировку. Авторизация загружается до бизнес-
транзакции, а аудит получает уже установленного автора запроса.

Адаптер поддерживает только используемые проектом конструкции: параметры
`?`, строковые и индексные обращения к row, известные `INSERT OR IGNORE`,
`INSERT OR REPLACE` для настроек, автоматические ID и `PRAGMA table_info`.
Это не универсальный эмулятор SQLite. JSON-аналитика имеет явный вариант SQL
для каждого backend. Новые специфичные SQL-запросы нужно проверять на обоих.

## Миграции

1. `0001_core.sql` — исходные бизнес-таблицы.
2. `0002_legacy_columns.json` — недостающие столбцы старого preview.
3. `0003_staff_and_safety.sql` — сотрудники, сессии, MFA, receipts запросов,
   история статусов и webhook inbox/leases.

`schema_migrations` хранит версию, SHA-256 и время применения. Повторный запуск
не изменяет данные. Несовпадение checksum и база с неизвестной новой миграцией
останавливают запуск. Уже применённые файлы менять нельзя: добавьте следующую
миграцию. DDL и запись версии находятся в одной транзакции.

```bash
.venv/bin/python scripts/db_manage.py status
.venv/bin/python scripts/db_manage.py migrate
```

`migrate` создаёт только схему; он не наполняет каталог и не включает реальные
заказы. Обычный запуск приложения выполняет миграции и предусмотренный seed
preview. `status` показывает версии и backend, без строки подключения.

## Перенос SQLite preview в PostgreSQL

Скрипт предназначен для синтетических preview-данных. Он проверяет целостность
SQLite, внешние ключи, известные таблицы и отсутствие реальных контактов в
заказах. Учётные записи сотрудников, MFA, сессии, login guards и незавершённые
webhook leases не копируются. Доступ сотрудников на целевой среде настраивается
отдельно.

```bash
.venv/bin/python scripts/db_transfer.py --source /path/to/preview.sqlite3
.venv/bin/python scripts/db_transfer.py --source /path/to/preview.sqlite3 --apply
```

Первая команда только читает локальный файл и показывает имена таблиц и число
строк. К целевой базе она не подключается. Вторая читает `DATABASE_URL` из
окружения, применяет миграции и копирует в пустые бизнес-таблицы одной
транзакцией. Источник остаётся неизменным. Совпадение числа строк и счётчики
генерации ID проверяются; ошибка откатывает и данные, и новые миграции. Слияние,
перезапись и удаление существующих записей не предусмотрены.

Перед согласованным переключением остановите запись источника, сделайте backup,
выполните dry-run, примените перенос в отдельную среду и проверьте заказы,
ledger и права. Для receipts и подписанных cookies нужен согласованный секрет
приложения; при его смене старые гостевые сессии и digest запросов не
восстанавливаются автоматически. Перенос коммерческих данных этим скриптом
сознательно заблокирован и требует отдельного миграционного проекта.

## Backup и восстановление

Локальная SQLite-копия создаётся штатным backup API, имеет права `0600` и
проверяется `integrity_check`. Существующий файл назначения не перезаписывается.

```bash
.venv/bin/python scripts/db_manage.py backup-sqlite --source /path/to/preview.sqlite3 --destination /path/to/backup.sqlite3
```

Для PostgreSQL используйте `pg_dump`/`pg_restore` соответствующей версии.
Задайте `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE` и секрет аутентификации через
менеджер секретов либо защищённый `PGPASSFILE`. Не помещайте URL с паролем
в аргументы команд или shell history.

```bash
pg_dump --format=custom --no-owner --no-acl --file=rakovar.dump
pg_restore --dbname=rakovar_restore --exit-on-error --single-transaction --no-owner --no-acl rakovar.dump
```

Восстанавливать нужно в отдельную заранее созданную пустую базу, с отдельными
правами. После восстановления сверить версии миграций, количество записей,
ledger и доступность приложения. Сам факт наличия dump не подтверждает
восстановимость. Для production ещё предстоит утвердить частоту копирования,
RPO/RTO, шифрование, срок хранения, внешнее хранение и ответственного за drill.

Откат приложения не откатывает БД, начисления и внешние события. У текущих
миграций нет destructive down-команд. Откат к старому приложению выполняется
только после проверки его совместимости с новой схемой. Полное восстановление
backup меняет состояние данных и требует отдельного согласованного плана.

## Реально выполненные проверки

Тестовый runner создаёт временный PostgreSQL, слушающий только loopback, и
удаляет кластер после завершения. Ускоренные настройки fsync в нём применяются
только к disposable тестам. Они не являются настройками для Render или
production.

```bash
.venv/bin/python scripts/run_postgres_tests.py --postgres-bin /path/to/postgresql/bin -- -q tests/test_storage.py tests/test_db_maintenance.py
```

Проверяются миграции старой схемы без потери строки, повторное применение и
checksum, rollback, продолжение транзакции после перехваченного конфликта,
генерация ID, параметризация, JSON-аналитика и конкурентные изменения.
Проверки обслуживания восстанавливают SQLite backup, копируют preview в
PostgreSQL, сверяют строки и sequence, отклоняют непустую цель и откатывают
ошибочный перенос. PostgreSQL dump дополнительно восстанавливается в отдельную
одноразовую базу, где проверяются записи и версии миграций.

`tests/conftest.py` при `RAKOVAR_TEST_POSTGRES=1` создаёт уникальную schema для
каждого теста. Ручной запуск с этим флагом допустим только с disposable
`TEST_POSTGRES_URL`: fixture создаёт и удаляет только свои schema. Для обычного
SQLite suite флаг не нужен.
