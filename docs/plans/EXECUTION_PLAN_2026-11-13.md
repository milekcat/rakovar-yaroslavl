### 0.3 Размер PR и Definition of Done

Каждый PR решает одну связную проблему и включает: цель / scope / out-of-scope / schema changes / API contracts / screen states / tests / security impact / migration plan / rollback / screenshots/видео **реально проверенных экранов**. ## 4. Этап 3 — единая идентичность покупателя и кабинет (P1)

**Deps:** ACC-01..07, ROLE-01, SECURITY-01.

- `customer_id` как immutable key, слой связи legacy `guest_id` и MAX `max_<id>`, отдельно identity providers и verified contacts.
- Автоучётная запись при **первом заказе**: подтверждение владения номером до выдачи приватного кабинета; при недоступности SMS — гостевой заказ без доступа к чужим данным. Phone E.164; email отдельно подтвердить.
- Генерировать one-time temporary password **только после OTP**, показать один раз с Copy на защищённом post-order экране, хранить только хеш, не передавать в analytics/email; принудительная смена по первому password-login.
- Восстановление через магазин (лично/звонок), но Caller ID не считается полноценной идентификацией; операторы проходят дополнительную проверку, выдают ограниченный reset token, отзывают сессии; при финансовых данных — step-up.
- VK ID: server verification OAuth/PKCE/state и проверка владельца перед bind/unbind. MAX Mini App: использовать существующую `max_auth.py` HMAC+freshness и привязку verified subject, не доверять `guest_id` из URL. Яндекс ID: OAuth со state/nonce и PKCE по поддерживаемому профилю; использовать только разрешённые attrs.
- Не объединять аккаунты только по email/телефону без владения обеими учётками. Транзакционная и идемпотентная миграция заказов, бонусов, адресов, сертификатов, чатов.
- Покупательский кабинет отдельными страницами /заказы/чат/балансы/сертификаты/настройки входа/согласия.

**Gate-3:** один заказ и подарочный баланс видны одному account при входе с телефона, VK, MAX, Яндекс после разрешённого связывания; idor и session fixation/test fail закрыты.

## 5. Этап 4 — заказы, доставка, переписка, курьер (P1)

**Deps:** ORD-01..05, ROLE-01, GOV-08.

- Три независимых автомата: заказ, оплата, доставка; смена статуса проверяет текущую версию/actor/role, идемпотентность и доступность всех side effects. Зафиксировать переходы в `order_events`.
- Checkout: сохранение формы/корзины, серверный расчёт (перед оплатой), способы получения, адрес, зоны, слоты, финальная проверка веса, подтверждение суммы. Дубли запросов не создают дубли заказов. Сценарии offline/timeout.
- Операторы: современная очередь, SLA, раздельный чат и внутренние заметки, назначение, причины отмены/замены, возвраты, audit.
- Курьер: только назначенные заказы, мобильно, навигация, подтверждение доставки, учёт наличных; PII минимум; карта только при законном основании и корректной политике.
- Уведомления: надёжный outbox, sender, retry, idempotency, error status; нет ложной отметки отправки.

**Gate-4:** E2E от нового заказа до вручения/самовывоза, отмена/возврат резерва, чат и курьерская авторизация без доступа к чужим данным; мобильная доставка понятна и работоспособна.

`expand → backfill → dual-read / feature flag → switch read → contract`. Не удалять старые поля `shop_accounts.email_digest`, `guest_id`, `shop_order_details` и`shop_bonus_ledger` до отдельного анализа consumers, миграции и согласования. Сущности/таблицы добавлять `UNIQUE`, foreign keys/checks, order of deploy и idempotent up/backfill. Под Postgres временно учитывать SQLite test semantics (не притворяться полной эквивалентностью).

Новые операции:
- stable customer ID mapping guest/max IDs, transactions, rollback with snapshot;
- product master/variant + channel offers; legacy catalog fallback while data verified;
- CMS blocks + media object store; rollback and garbage collection;
- new order/payment/delivery states; canonical snapshots and transition history;
- gift certificate accounting and webhook handling. У всех финансовых записей неизменяемые refs и воспроизводимые reconciliation checks.

## 11. Проверки на непротиворечивость

- **Privacy:** внешние Google/Meta/VK/MAX/Yandex, письмо и чек разные цели и правовые основания; не публиковать чужие отзывы/профили и не копировать закрытые данные.
- **Accuracy:** адрес Комсомольская 14 и рейтинги из актуальной карточки — snapshots, не годовая гарантия, цены — исторические наблюдения.
- **UX truth:** без технических шаблонов/AI-воды, «готово» только когда API подтвердил факт, при ошибке не обещать выполненное действие.
- **Financial:** 2 параллельных checkout, 2 webhook, 2 redeem и 2 staff action не создают дубликаты или отрицательный неразрешённый денежный остаток.
- **Staff:** доступ по role+object, MFA, аудит; скрытый URL `/team/rakovar-control/login` — не основное средство защиты.
- **Review:** отзывы старого/нового адреса и чужого города не суммируются, негатив не стирается ради маркетинга.

## 12. Как сдавать результат по этапам

На каждом этапе исполнитель присылает:

| Поле | Значение |
|---|---|
| `STATUS` | DESIGNED / IMPLEMENTED / TESTED / NOT_VERIFIED / BLOCKED |
| `BRANCH / COMMIT / PR` | Реальные ID и ссылки |
| `CHANGED FILES` | Фактический список |
| `API / SCHEMA` | Новый контракт и миграция; `none` если нет |
| `TESTS RUN` | Команды + результат/число тестов; не обещания |
| `UI` | Реальные скриншоты desktop/mobile и экранные состояния либо NOT_VERIFIED |
| `SECURITY / DATA` | Чувствительные изменения, секреты не раскрывать |
| `ROLLBACK` | Как вернуть поведение, какие данные останутся |
| `OWNER INPUT` | Только конкретные заблокировавшие бизнес-данные |
| `NEXT` | Следующий доступный эпик/задача |

Если задача занимает несколько сессий, вести журнал в GitHub (issue/PR/checklist). **Не утверждать, что агент продолжает работу в фоне, пока это реально не оформлено в Tasks или automation.**

## 13. Синхронизация прогресса

Точкой правды служит GitHub: branch, PR, issue и tests. Модель может предложить вариант, но после каждого шага надо анализировать diff и действительно запускать проверки. Не засчитывать полностью функциональную административную систему по наличию кнопок без серверной реализации и обоснованного permission enforcement.

Сохранить README и историческую документацию; устаревшие описания маркировать `SUPERSEDED` после проверки, не удалять. Декомпозировать работу по ID из backlog; не делать один монолитный «feat: redesign everything» PR.

**Это план, не отчёт о внедрении.**
