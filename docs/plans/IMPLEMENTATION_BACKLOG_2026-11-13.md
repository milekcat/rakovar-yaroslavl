# РАКОВАРЪ 2.0 — реализационный backlog

**Дата:** 13.11.2026. **Статус:** PROPOSED; задачи **не реализованы** этим документационным PR. Полная система требований: [MASTER_SPEC_2026-11-13.md](MASTER_SPEC_2026-11-13.md). Схема для автоматизации — [implementation-backlog-2026-11-13.csv](implementation-backlog-2026-11-13.csv).

## Правила исполнения

- Порядок P0 → P1 → P2 → P3; зависимости важнее номера приоритета. Статус конкретной задачи подтверждается кодом, тестами и приёмкой; одно наличие ТЗ не равно реализации.
- Каждое изменение: проверить текущее дерево, AGENTS.md (если появится), миграции/legacy/routes, написать решение → совместимый diff → tests → review → deployment только с разрешения.
- Деньги, ПД, реквизиты, реальные аккаунты, секреты, prod и платежи — **нет автоматического включения** без верификации владельца и юридической приёмки.
- Внешний импорт не перезаписывает `data/catalog.json` и production-БД без manual approval; каждая позиция и фото имеют provenance.

## Gates для реальных операций

1. **Catalog gate:** полная выгрузка доступных площадок + подтверждение продавцом цены/состава/остатка/фото, разрешённые способы оплаты и транспортировки.
2. **Identity gate:** подтвержденные контакты/связи; нельзя владеть чужим счётом по номеру/почте/социальному subject без identity proof.
3. **Payment gate:** sandbox test/real seller merchant, ККТ, 54-ФЗ, провайдерские idempotency и webhook replay, разрешение на возвраты.
4. **Security gate:** DPIA/локализация по 152-ФЗ с юристом, минимальные права, MFA, утечка PII и логирование.
5. **Operations gate:** PostgreSQL backup/restore before 10.12.2026; CI, migration rollback, staging smoke, own UAT.
6. **Launch gate:** отдельное разрешение владельца на деплой и публикацию цен; no silent main merge or prod deploy.

## Разделение эпиков

- Governance/data: GOV, CAT, QA-01.
- Core website/UI/CMS: WEB, CMS.
- Identity & operations: ACC, ORD, ROLE.
- Financial: PAY, FIN, LEGAL.
- Retention & community: LOY, MKT.
- Release/channel apps: APP, QA-02..04.

Каждый epic надо разбить на разработческие PR с конкретными таблицами, контрактами, UI state matrix, upgrade/rollback SQL и тестами; большой единовременный rewrite запрещён.
