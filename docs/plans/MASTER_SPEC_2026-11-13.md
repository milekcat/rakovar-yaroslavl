## 1. Бизнес и каталог

РАКОВАРЪ объединяет **магазин морепродуктов**, **приготовление блюд под заказ**, **сеты/кейтеринг**, **съедобные букеты и подарки**, **сезонную торговлю/предзаказ**. Эти бизнес-режимы различаются условиями, временем приготовления, способами упаковки и оплаты.

### 1.1 Модель мастер-товара

Основные сущности:

- `products` — канонический продукт (title, category, copy, lifecycle, slug, brand/source, seller_id, tags).
- `product_variants` — SKU с размером/весом/способом приготовления/упаковкой, `unit`, `quantity_step`, `min_qty`, `max_qty`.
- `channel_offers` — отдельно цена/активность/внешний ID для own-web, VK, MAX, Yandex Eda, Chibbis. Не связывать их ценой «одинаково для всех».
- `price_observations` — внешние наблюдения с URL, временем, площадкой и скриншотным/сырьевым хешем; **не действующий ценник**.
- `approved_prices` — действующая цена и сроки действия, утверждающий сотрудник, валюта/единица, история.
- `inventory_lots`, `inventory_movements`, `reservations` — остаток, партии, условия хранения, резервы; режим `made_to_order` отдельно от `stocked`.
- `product_media`, `media_assets` — точные изображения, авторские права, alt, фокусная точка, responsive variants, status.
- `product_composition`, `food_allergens`, `prep_options` — состав, выход, предупреждения, сроки и условия хранения; только подтверждённые данные.
- `import_matches` — сопоставление внешнего названия/ID к master SKU с уверенностью, подтверждением и журналом.

Применять жизненный цикл `discovered → draft → evidence_review → approved → published → archived`. Нет автоматической продажи без утверждённого варианта, цены и правил исполнения. Отдельный каталог сезонных партий и предзаказов, с датой поступления/окном выдачи.

Header (компактный desktop/mobile), мегаменю каталога, доступный поиск с подсказками, геозона/адрес, статусы магазина, корзина/избранное/профиль; footer с компанией, контактами, условиями и обязательными правовыми ссылками. На мобильном фильтры — sheet, на desktop — sidebar. В админке и кабинете курьера своя мобильная компоновка, не сжатая трёхколоночная таблица. ## 3. Регистрация / единая идентичность

**Один `customer_id` → несколько identity-провайдеров**: телефон, VK ID, MAX Mini App, Yandex ID. Старые `guest_id` и `max_guest_id` — совместимый переходный слой, не деньги/владение по открытой строке.

- `customer_identities(customer_id, provider, provider_subject, bound_at, verified_at, revoked_at)` с UNIQUE `(provider,provider_subject)`; `customer_contacts` (phone E.164, email, verified flags), `customer_sessions`, `customer_consents`, `identity_audit`.
- Из VK: VK ID SDK OAuth 2.1/PKCE на собственном сайте; подтверждённый external subject. В MAX Mini App — серверная проверка подписи и свежести `initData` (часть уже есть в `max_auth.py`); номер запросить через разрешённый интерфейс, не приписывать самовольно. В Yandex ID — OAuth2 и nonce/state+PKCE когда поддерживается профилем интеграции.
- Переход из группы VK/мини-аппа предлагает соответствующий способ входа, но **не открывает доступ к чужим данным без проверки**. VK web-link ≠ доказанная авторизация. Внешний provider ID не может привязываться ко второму account без безопасного merge review.
- Первый checkout: имя, телефон, email, условия; OTP владения телефоном; в случае неготового SMS заказ гостевой без раскрытия приватного кабинета. Затем автоматическое создание/привязка профиля и заказ. Телефон — основной логин; email подтверждается отдельно.
- Пароль: криптостойкий одноразовый временный пароль после проверки номера, показ **один раз** на защищённой странице с copy, хеш на сервере, принудительная смена при первом password-login. **Не отсылать пароль в email, SMS, аналитику или логи**. Соцавторизация не должна принуждать вводить временный пароль.
- По требованию владельца самостоятельное восстановление пароля отключено: заявка лично или при звонке с привязанного номера в магазин. **Caller ID недостаточен**; оператор выполняет дополнительную проверку, формирует ограниченный reset token, отзывает прежние сессии и журналирует факт. Для финансового баланса — усиленная проверка.
- Merge аккаунтов: никогда только по совпавшему номеру/email/имени; обязательное доказательство владения двумя identity; транзакционная миграция ключей заказа/балансов с сохранением ledger/source IDs и ревизионным журналом. Тесты параллельного входа/привязки/merge.

## 4. Транзакционный commerce и заказ

Разделить **order state**, **payment state**, **fulfilment/delivery state**, **refund state**; не перегружать один `orders.status`.

Путь: **корзина → серверный quote → контакты/доставка/слот → способ оплаты → подтверждение → очередь кухни/склада → курьер/самовывоз → вручение → чек/закрытие/отзыв**. Для весовых товаров: подтверждение окончательного веса и суммы покупателем/разрешённый двухэтапный платёж, иначе не списывать больше подтверждённого.

- Заказы: immutable `order_items` snapshot (цена, SKU, налоговые параметры, вес, способ), `order_events`, `payment_events`, `delivery_events`, `order_assignments`, `order_chat_messages`, `receipts`, `refunds`.
- Статусы исполнения: new → accepted → preparing → ready_for_pickup → handed_to_courier → delivered/collected; cancel/reject/return через разрешённые переходы. Для каждой операции: actor, reason, timestamp, origin channel, idempotency.
- Варианты получения: самовывоз и доставка с проверкой геозон, стоимости и фактически доступного окна. Удалять товар при нехватке остатков молча запрещено; товар требует согласованной замены.
- Внутри заказа чат: customer↔assigned staff, вложения только с проверкой формата/размера, SLA/unread, системные события отделены от сообщений. **Внутренние заметки менеджеров никогда не уходят клиенту**.
- Корзина сохраняется между страницами, guest и account при законном подтверждении; защита от дубля оформления по key; сервер — единственный источник цены, бонусов, статуса и доступности.
- Интерфейс курьера: только назначенные активные заказы, крупные действия, маршрут/контакт с маскировкой, приём наличных, фото/код подтверждения выдачи при законном основании, журнал, офлайн-очередь только безопасных действий; геолокация отдельно согласована по цели/срокам.
- Сотрудники: owner, system_admin, store_manager, order_manager, warehouse, courier_dispatcher, courier, storefront_editor, social_media_editor, marketing, support, finance, partner, customer. RBAC + object scopes (склад/площадка/назначенный заказ) + server enforcement + MFA для чувствительных операций.

## 5. Платежи, счета, сертификаты

**Предлагаемые способы расчёта:** ЮKassa (банковская карта и поддерживаемые методы, в т.ч. СБП), наличные при получении, оплата по счёту бизнеса, предоплата по подарочному сертификату. «Перевод онлайн» — только на реквизиты действительного продавца, не личные карты сотрудников. Оплата по счёту требует сверки до `paid`.

- Контур `payments` с provider object IDs, idempotency, серверным webhook signature/auth verification, monotonic state machine, retry/outbox, double-entry-like journal и reconciliation. Success redirect **не подтверждает** факт оплаты. Сумма и валюта фиксируются на сервере. Нет хранения PAN/CVV.
- `fiscal_receipts`: события расчёта, корректировка/возврат, 54-ФЗ, параметры товаров/ставок/признаков расчёта — на основании данных реального продавца и кассового провайдера. Чек не равен письму «заказ принят». Отправлять предусмотренным законным способом на подтверждённые контакты.
- **Раздельные финансовые типы:** бонусные баллы (скидка), выданный компанией promo credit, подарочная **предоплата от продажи сертификата**, возможная денежная предоплата от клиента — только после правовой квалификации в связи с 161-ФЗ. Нельзя смешивать даже в одном ledger.
- Сертификат: покупка → pending_payment → платёж confirmed → выпущенный непрогнозируемый код/QR/PDF → передача → одна атомарная активация в проверенном аккаунте → предоплаченный ledger credit → частичные списания и возвраты; покупки сертификатов не дают автоматически право незаконно «сжечь» остаток. Сертификат не должен превращаться в переводимый без ограничений электронный кошелёк. Ограничения, возвраты и кассовые чеки утверждаются юристом.
- Админка сертификатов: шаблоны/номиналы/дизайны, партии, номера, статусы, частичные балансы, источники средств, возвраты, fraud/audit; отдельно промосертификаты компании/партнёров.
- Промокоды на личный счёт: **промокод никогда сам по себе не авторизует списание чужих денег**. Только подтверждённый account и транзакционная проверка ownership.
- При отменах: compensating entries, reversal бонусов/призов, stock release, возврат предоплаты, контроль double spend при параллельных операциях.

## 6. Клуб, колесо, партнёры, акции

- Клуб: loyalty ledger, earn/redeem/expiry по согласованным правилам, отдельная история клиента, серверная идемпотентность; не начислять за неоплаченный заказ.
- Колесо: `campaign`, `sectors`, `reward_kind`, `weights`, `limits`, `stock`, `budgets`, `redemption_window`, `eligibility`, `partner_id`. Победитель определяется **сервером**, анимация отображает уже определённый результат. Версионировать опубликованные вероятности/правила и все изменения.
- Партнёрский подарок: источник/себестоимость/спонсор, количество, SKU/код выдачи, срок, назначенное лицо, правила получения/верификации, подтверждение исполнения, возвраты, отчётность; интеграция с партнёрами (например, Перфлюенс) только после договора/API разрешения.
- Акции: видимость по времени/каналу/товару/аудитории, совместимость с бонусами/сертификатами, согласованный бюджет, промокоды, статистика, баннеры и целевые страницы.
- Промо-правила и рекламные маркировки/согласия юридически проверяются; не строить платную азартную механику.

## 7. VK / MAX / Yandex, публикации, уведомления, коммуникации

- Auth ≠ возможность написать от имени сообщества. Отдельные разрешения VK сообщений, канал/чат MAX после `bot_started`, opt-in маркетинга для каждого канала и отзыва согласия. Отсутствие канала не блокирует заказы.
- Центр коммуникаций: templates по событиям `order_accepted`, `preparing`, `ready`, `courier_assigned`, `payment_succeeded`, `certificate_issued`, `refund_completed`. Маршрутизация на подтверждённый email/телефон/VK/MAX с журналом `queued/sent/ack/failed`, retries, dedupe и механизмом ручной обработки неопределённых ответов.
- Чеки и транзакционные уведомления отделены от рекламы; согласие на маркетинг не предзаполнено.
- Контент-редактор: черновики/медиа/календарь/подтверждение публикации. VK wall, MAX messages API, другие каналы при подтверждённой документации и правах. Нельзя обещать API-публикацию для функции, не поддерживаемой текущим API провайдера.
- Метрики каналов: UTM, order attribution, конверсия, стоимость, ошибки отправки; хранение без избыточных персональных данных.

## 12. Проверяемые критерии приёмки верхнего уровня

**Каталог:** всё, что публично продаётся, сопоставлено с утверждённой SKU-карточкой; нет неверных весов, чужих фото, неподтверждённых цен/доступности; единый каталог и канал-специфичные цены управляются раздельно.
