# Доступ сотрудников — P0

Индивидуальные учётные записи, серверный RBAC, отзыв сессий и TOTP реализованы в `staff_auth.py`. Пароли хранятся в виде хешей Werkzeug; в базе хранится SHA-256 токена сессии, а не сам токен. Старый `session['admin']` оставлен для отображения интерфейса и не предоставляет доступ.

Проверка модуля: одинаковые 21 тест прошли на временной SQLite БД и на изолированном локальном PostgreSQL 17.11. Использованы настоящие Flask-запросы и транзакции `storage.connect_database`. Сквозная проверка всего приложения фиксируется в общем отчёте проекта отдельно.

## Вход и первоначальная настройка

Существующий `ADMIN_PASSWORD_HASH` — bootstrap-учётная запись `owner`. Пустое поле username при входе совместимо с прежней формой. Bootstrap-пароль меняется через секрет окружения, а не через API. Смена его хеша отзывает ранее выданные bootstrap-сессии. Новые сотрудники создаются отдельно; username `owner` зарезервирован.

Обязательная MFA включается через `STAFF_REQUIRE_MFA=true`; вне demo приложение требует её для `owner` и `admin` независимо от флага. Если MFA ещё не настроена, привилегированный вход отклоняется с `mfa_enrollment_required`. Пароль не даёт обхода этого ограничения.

Первоначальную настройку выполняют **до** включения обязательной MFA в изолированном staging с постоянной БД этой среды:

1. Ограничить доступ к среде доверенными операторами, оставить `DEMO_MODE=true` и `STAFF_REQUIRE_MFA=false`. Реальные клиентские данные не вносить.
2. Войти как `owner` с bootstrap-паролем. Для сотрудника войти под его отдельной учётной записью.
3. Передать текущий пароль в `POST /api/admin/security/mfa/enroll` с CSRF-заголовком. Ответ содержит секрет настройки для аутентификатора; его нельзя сохранять в логах, скриншотах или репозитории.
4. В течение 10 минут подтвердить шестизначный код через `POST /api/admin/security/mfa/confirm`.
5. Завершить сессию и проверить вход с новым кодом. Код, использованный для подтверждения, уже израсходован; дождаться следующего 30-секундного шага.
6. Проверить MFA всех `owner` и `admin`, после чего включить `STAFF_REQUIRE_MFA=true` и проверить отказ входа без OTP. Перенос в будущую production-среду требует отдельной процедуры развёртывания auth registry; демонстрационные торговые данные не следует переносить вместе с ним.

Не отключать обязательную MFA на открытом production-сервисе для регистрации или восстановления доступа. Автоматический recovery/disable API не реализован. Потеря аутентификатора требует отдельно согласованной процедуры доверенного оператора БД; обычная смена bootstrap-пароля не сбрасывает MFA.

## Роли и действующие права

Новая серверная ручка должна быть явно внесена в `ENDPOINT_PERMISSIONS`. Неизвестная ручка отклоняется даже для owner. Клиентское скрытие кнопок не заменяет эту проверку.

| Роль | Разрешённые действия |
|---|---|
| `owner` | Все явно классифицированные действия, включая создание owner/admin |
| `admin` | Управление действующими модулями и непривилегированными сотрудниками; не может создавать/изменять owner/admin |
| `store_manager` | Обзор, чтение/изменение заказов и каталога; чтение акций, игр, лояльности и настроек |
| `catalog_manager` | Чтение и изменение каталога |
| `warehouse_operator` | Чтение каталога; складские операции появятся с отдельным модулем P1 |
| `order_manager` | Чтение/изменение заказов, чтение каталога |
| `marketing_manager` | Акции, игры, контент, лояльность; чтение интеграций и аналитики |
| `content_editor` | Чтение/изменение контента, чтение каталога |
| `courier` | Только вход в оболочку; кабинет доставки P1 ещё не реализован |
| `customer_support` | Чтение заказов и каталога |
| `finance_analyst` | Чтение обзора, заказов, аналитики и лояльности |
| `partner` | Только вход в оболочку; отдельные партнёрские функции ещё не реализованы |

У всех ролей есть личные настройки безопасности. Только owner/admin с `staff.manage` видят список сотрудников и журнал входов. Изменение роли, пароля или блокировка сотрудника увеличивает версию учётных данных и отзывает все его сессии. Самому себе нельзя изменить роль или сбросить пароль через управление сотрудниками; для пароля есть личный API с повторной проверкой текущего пароля.

## API

Все изменения требуют `X-CSRF-Token` из текущей staff-сессии. Ответы безопасности имеют `Cache-Control: no-store`. Пароли и MFA-секреты передаются только по HTTPS; в примерах ниже намеренно нет действующих значений.

| Метод и путь | Контракт |
|---|---|
| `GET /api/admin/security/me` | Текущие `id`, `username`, `role`, `session_id`, `mfa_enabled`, `permissions` |
| `GET /api/admin/staff` | `accounts`, список `roles`, признак bootstrap-owner; без password hashes/секретов |
| `POST /api/admin/staff` | `{username, password, role}`; пароль 12–256 символов |
| `PATCH /api/admin/staff/<id>` | Любое сочетание `{active: boolean, role, password}`; другие поля запрещены |
| `GET /api/admin/security/sessions` | Собственные сессии, время создания/истечения/отзыва и признак current; без токенов |
| `DELETE /api/admin/security/sessions/<id>` | Отзыв собственной сессии; сессия другого сотрудника недоступна |
| `POST /api/admin/security/password` | `{password, new_password}`; после успеха нужен повторный вход |
| `POST /api/admin/security/mfa/enroll` | `{password}`; возвращает provisioning secret на 10 минут |
| `POST /api/admin/security/mfa/confirm` | `{code}`; включает MFA и отзывает остальные сессии |
| `GET /api/admin/security/login-events` | Журнал исходов входа с хешированным subject; только `staff.manage` |

После пяти ошибок входа, повторной проверки пароля или подтверждения MFA соответствующая группа попыток блокируется на 15 минут. Счётчики находятся в БД и сохраняются после отклонённого запроса. OTP принимается в текущем либо соседнем 30-секундном шаге; использованный шаг нельзя применить повторно.

## Сессии и аудит

На каждом HTTP-запросе authority заново проверяется в registry БД. Внутри одного запроса principal кэшируется в `flask.g`, чтобы аудит из бизнес-транзакции не открывал вторую транзакцию с той же блокировкой. Кэш сбрасывается при ротации/завершении сессии и подтверждении MFA. Глобального кэша прав между запросами нет.

Staff и покупатель пока используют одну подписанную cookie. Вход/выход сотрудников сохраняет только ранее подписанные shopper-поля `guest_id`, `max_guest_id`, `max_user_id`, `max_auth_date`, `public_csrf`. Staff token и staff CSRF меняются, все прочие поля удаляются. Это сохраняет идентичность покупателя и не позволяет назначить её через тело запроса.

Audit содержит staff ID, действие и безопасные атрибуты, например роль или факт сброса пароля. Пароли, хеши паролей, токены сессий и provisioning seeds не записываются в аудит или журнал входов.

## Границы готовности

- Секреты TOTP и незавершённой настройки сейчас хранятся в БД открытым текстом. Перед commercial launch нужны согласованное шифрование на уровне приложения/управляемое хранилище ключей, защищённые резервные копии и процедура ротации. P0 не заявляет завершённую production-защиту MFA secrets.
- Нет recovery codes, self-service сброса MFA, SSO и восстановления пароля по почте. Отсутствие этих функций не создаёт обхода проверок.
- MFA обязательно для owner/admin при включённом требовании; дополнительные роли можно расширить отдельной политикой. До реальных персональных данных нужны пересмотр минимальных прав, ограничения доступа к контактам и фильтрация данных по назначенным заказам.
- Courier/warehouse/partner в матрице — права на имеющиеся ручки, а не реализованные рабочие кабинеты.
