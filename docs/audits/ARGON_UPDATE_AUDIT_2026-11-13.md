# Аудит пакета Gemini Argon — решение по интеграции

**Дата проверки:** 13.11.2026  
**Артефакт:** `rakovar_yaroslavl_v2_implementation-1.zip` (2,543,649 байт; 175 файлов; 2,826,427 байт распакованного содержимого).  
**Объект:** архивная Git-ветка `feat/rakovar-v2-multipage-storefront`, цепочка PR1–PR5 и Android-пакет.  
**Решение:** **НЕ СЛИВАТЬ и НЕ РАЗВЁРТЫВАТЬ**. Использовать только как источник UX-идей; переносить отдельные элементы после адаптации к актуальному `main`.

## 1. Сверка происхождения и актуальности

Архив содержит собственный локальный Git-репозиторий, но не настроенный remote. Его `main` — `be66369`; HEAD веток `feat/pr5-android-shell-and-hybrid-db` и `feat/rakovar-v2-multipage-storefront` — `730c262`. В архиве нет коммита `c16b378`, указанного в сопроводительном отчёте. Обе названные ветки в архиве указывают на один и тот же HEAD `730c262`; отдельного дополнительного коммита после PR5 нет. В архиве также есть незакоммиченные `deploy_to_github_and_render.sh` и `static/images/uploads/media_d20f6ffd523b78a8.jpg`.

На GitHub ветки `feat/rakovar-v2-multipage-storefront` и `feat/pr1...`–`feat/pr5...` не найдены. PR #7 — документационный PR и не содержит эту реализацию. Его база `main` отличается от архивного `be66369`; архив не является актуальной веткой репозитория и не может быть слит без переноса изменений поверх текущего кода.

**Критически важно:** актуальный `main` уже содержит отдельную Flask-архитектуру, `storage.py` с PostgreSQL bridge, `staff_auth.py` с индивидуальными учётными записями/RBAC/MFA, `commerce_safety.py` с CSRF/idempotency support, шифрование клиентских данных и семь миграций по README. Архив заменяет этот фундамент самостоятельным WSGI/SQLite-приложением. Полный импорт приведёт к регрессии и потере уже выполненных защит.

## 2. Что в архиве действительно есть

- 9 категорий и 74 карточки в `catalog_seed.py`; 74 шаблонных URL страницы товаров проверяются внутренним тестовым клиентом.
- Отдельные Jinja-шаблоны главной, каталога, категории, товара, checkout, отзывов, клуба, доставки, аккаунта и админки.
- Базовые экраны CMS, загрузки изображений, заказов, сертификатов, бонусов, колеса, контент-плана и курьерских ролей.
- Android source fragment и APK с заявленной версией 2.0.0.
- Пять JavaScript-файлов проходят синтаксическую проверку.

Это полезный **UX-прототип и перечень сценариев**, но наличие обработчика/шаблона не подтверждает безопасную или реальную интеграцию внешнего сервиса.

## 3. Критические дефекты — P0, блокируют любой production

### P0.1 — известные fallback-секреты и пароли сотрудников

В `app.py` заданы постоянные значения по умолчанию для Flask secret, администратора, оператора, курьера и webhook-секрета; вход допускает также общий запасной пароль. Это позволяет входить в административную систему без индивидуально выданных учётных данных. В тесте архивной реализации POST на служебный вход с известным fallback-паролем вернул 302 и установил `staff_role=admin`.

**Требование:** никаких production fallback credentials; обязательная конфигурационная проверка при старте, индивидуальные аккаунты, MFA, отзыв сессий и аудит. Не переносить значения секретов в документацию или новые конфигурации.

### P0.2 — телефонная авторизация фактически не подтверждает владение номером

При стандартной конфигурации `RAKOVAR_TEST_MODE` включён по умолчанию, а код подтверждения фиксирован. SMS-провайдер не вызывается. API отвечает, что код отправлен, хотя сообщения нет. Проверка в архиве подтвердила фиксированный код в session state.

**Требование:** тестовый режим должен быть явно включён только в тестовом окружении; в production без активного SMS/OTP provider endpoint должен отвечать `503`, не создавать сессию и не выдавать фиктивное подтверждение. Добавить TTL, одноразовость, лимиты отправки и попыток, защиту от перебора.

### P0.3 — социальная привязка принимает непроверенный внешний ID

`/api/auth/social-link` принимает переданный клиентом `external_id`. VK ID и Яндекс ID не проходят OAuth-проверку. Проверка MAX необязательна: при отсутствии bot token или initData внешний ID всё равно принимается. В изолированном тесте произвольный VK ID был успешно привязан.

**Требование:** серверный OAuth code exchange, проверка issuer/audience/state/nonce/redirect URI и уникальности identity; MAX — только после строгой проверки подписанного и не просроченного initData. Не принимать external ID из произвольного JSON.

### P0.4 — фиктивное подтверждение ЮKassa и 54-ФЗ

Webhook принимает самодельную HMAC-подпись из заголовка/JSON с fallback-секретом. Это не подтверждает фактическую транзакцию у ЮKassa. После такой проверки приложение само создаёт фиктивный номер чека и выставляет статус `fiscalized_54fz`. В изолированном тесте поддельный webhook с известной схемой вернул `payment_confirmed`.

**Требование:** до подключения реального провайдера отключить платёжный webhook и все переходы в paid/fiscalized. После подключения — проверять подлинность события и факт платежа через официальный API ЮKassa, сверять shop/order/amount/currency/status, обеспечивать идемпотентность по provider payment ID; фискальный статус менять только по подтверждению реальной ККТ/ОФД/чека.

### P0.5 — бесплатная выдача денежных сертификатов

`/api/certificates/issue` доступен анонимно, создаёт сертификат с полным номиналом и не требует оплаты или существующего заказа. Тест без авторизации получил активный сертификат номиналом 10 000 ₽.

**Требование:** выдача только после подтверждённой оплаты заказа на сертификат или авторизованной административной операции с журналом; до этого публичную выдачу отключить. Баланс сертификата — отдельный финансовый ledger, атомарное списание и возврат, защита от параллельного использования.

### P0.6 — PostgreSQL заявлен, но фактически не используется

`get_db_connection()` всегда открывает SQLite. `DATABASE_URL` используется для текстовой индикации в health response, но не для выбора драйвера. Миграция использует SQLite-специфичный `AUTOINCREMENT`, запросы `INSERT OR REPLACE` и placeholder `?`. Проверка с PostgreSQL URL показала фактический файл SQLite через `PRAGMA database_list`.

**Требование:** использовать актуальный `storage.py` текущего main и его миграционный механизм. Не заменять PostgreSQL bridge архивным кодом. Перед запуском провести тест на отдельной PostgreSQL базе.

### P0.7 — stored XSS из-за выключенного autoescape

Jinja `Environment` создаётся без `select_autoescape`; проверка `jinja_env.autoescape('html')` вернула `False`. Значения CMS/товара, выведенные без фильтрации, могут интерпретироваться браузером как HTML/JS.

**Требование:** autoescape для HTML/XML по умолчанию, безопасная схема CMS, sanitization только для разрешённого rich text, тесты на сохранённый XSS.

### P0.8 — traversal в обработчике static-файлов

Путь проверяется через `startswith(STATIC_DIR)`, что не является проверкой принадлежности пути каталогу. Запрос с переходом в соседний каталог с префиксом `static` успешно прочитал тестовый файл вне `static/`.

**Требование:** `Path.resolve()` + проверка `os.path.commonpath`/относительного пути, запрет symlink escape и отдельный тест traversal.

### P0.9 — сессии не пригодны для нескольких production workers

Сессии находятся в словаре процесса WSGI; cookie не подписана Flask и не имеет `Secure`. Данные теряются при перезапуске и не разделяются между Gunicorn workers. Сессия не ротируется надлежащим образом после входа.

**Требование:** сохранить текущую Flask session/StaffAccess реализацию main, cookie Secure/HttpOnly/SameSite, server-side revocable sessions и тесты на несколько workers.

### P0.10 — APK не подтверждён как устанавливаемый Android-клиент

APK имеет размер 3 509 байт; внутри `classes.dex` — 136 байт, `resources.arsc` — 36 байт, `AndroidManifest.xml` лежит как текстовый XML. В архиве нет Gradle wrapper, `build.gradle`, `settings.gradle`, ресурсов приложения и воспроизводимого build pipeline. Исходник MainActivity указывает на старый адрес `rakovar-yaroslavl.onrender.com`. Сертификат публичный, закрытого signing key/build setup нет.

**Решение:** APK не распространять и не публиковать на сайте как готовое приложение. Сначала создать воспроизводимый Android project с Gradle, реальной binary manifest/classes, подписать ключом владельца в CI secret store, проверить `apksigner verify`, install/launch на эмуляторе и HTTPS allowlist. OTA обновления не принимать без проверки подписи/хеша и безопасной установки.

## 4. Существенные дефекты — P1

- **Каталог и остатки:** 74 позиции используют только пять общих фотографий (32 позиции — одна фотография раков; 22 — одна фотография креветок). Цены, веса, остатки по двум адресам и межканальные цены зашиты в seed без подтверждения продавцом. После тестового заказа остаток не уменьшился (проверено: до и после осталось 48). Это допускает перепродажу. В текущем main уже есть curated catalog, 59 карточек для покупки, 15 черновиков, source evidence и 28 фото — сохранить его как источник истины.
- **Отзывы и рейтинги:** шесть отзывов, авторы, тексты и номера заказов зашиты как демонстрационные записи; рейтинги и счётчики заданы константами. Нет доказательства подлинности. Не публиковать. Использовать только отзывы из проверяемых источников и с разрешением на показ.
- **Партнёрские подарки и акции:** названия партнёров, призы, промокоды и даты кампаний зашиты в seed. Не активировать без договорённостей и подтверждения компании.
- **Колесо:** веса секторов заданы константами; `daily_max` не применяется к розыгрышу; партнёрский приз не резервируется по реальному остатку партнёра. Есть риск обещать отсутствующий подарок и превышать лимит.
- **Сертификаты:** баланс списывается до подтверждения оплаты заказа; нет полноценной атомарной блокировки/проверки владельца при списании; возврат через тестовую админ-логику не является возвратом денег.
- **Заказы:** наличие проверяется суммарно по двум складам, но склад не резервируется и не уменьшается. Выбранный филиал не определяет доступный остаток. Неподдерживаемые weight/cook labels не всегда отклоняются, а заменяются базовой ценой. Нет полной матрицы допустимых переходов статусов.
- **Курьеры и роли:** общий пароль на роль, нет индивидуальных учётных записей/назначения заказа курьеру; курьер может видеть общий список заказов и менять статус чужого заказа.
- **CSRF и rate limits:** в архивном custom WSGI API отсутствует полноценная CSRF-защита и лимитирование OTP/логина/сертификатов/сообщений.
- **CMS/media:** upload пишет в локальный `static/images/uploads`; это не постоянное объектное хранилище и может пропасть при redeploy. Проверяется сигнатура файла, но не декодирование/перекодирование изображения; для WebP неверно записывается MIME.
- **Социальные сети:** content plan только сохраняет запись в БД. Фактической публикации VK/MAX и подтверждения доставки в архиве нет.
- **Платёжная форма:** в заказе нет реального create-payment flow ЮKassa; webhook не заменяет его. Наличные/перевод и фискализация не подтверждены.
- **Возрастные ограничения:** флаг `age_18_confirmed` приходит от браузера и является самоотметкой, не проверкой возраста/личности.
- **Пароли покупателей:** фиксированная соль в PBKDF2 и отсутствие полноценного входа/смены пароля; `verify_password` не образует завершённый login flow.

## 6. Несоответствие документации текущему GitHub main

README текущего `main` описывает `/api/store/orders`, аккаунт `/account` и семь миграций. Но в проверенном `app.py` текущего `main` (blob SHA `d6225883cb8cac203365e392c814b702bb0eca33`) route decorators содержат `/api/orders`, `/` и административные/API маршруты; маршрутов `/api/store/orders` и HTML `/account` не найдено. Тест `tests/test_shop.py` обращается к `/api/store/orders`. Это отдельное несоответствие текущего репозитория, которое необходимо разрешить до заявления о полном прохождении shop tests. Не считать README доказательством существования маршрута.

В то же время актуальный main содержит важные модули, которых нет в архивном backend: PostgreSQL bridge, шифрование персональных данных, индивидуальный StaffAccess/RBAC/MFA, CSRF и idempotency support. Их нельзя заменять старым кодом.

## 7. Решение по интеграции

| Часть архива | Решение |
|---|---|
| Многостраничная карта: каталог, категория, товар, отзывы, доставка, клуб | **PORT AFTER REWORK** — адаптировать шаблоны и URL к актуальному Flask main и его API |
| Визуальные идеи/мобильные блоки | **REFERENCE ONLY** — сохранить полезные композиции после UX review |
| Старый `app.py`, `max_auth.py`, схема SQLite и WSGI session store | **REJECT** — не переносить |
| `catalog_seed.py`, отзывы, цены, остатки, партнёры, акции | **REJECT AS SOURCE OF TRUTH** — оставить только сверяемые кандидаты; данные владельца и текущие research manifests главнее |
| CMS/admin templates | **PORT SELECTIVELY** — сохранить текущие RBAC, аудит, медиа и settings API |
| Android APK/certificate | **REJECT** — не публиковать; собрать заново воспроизводимо |
| `deploy_to_github_and_render.sh` | **DO NOT RUN** — скрипт отправляет все ветки без тестового/PR gate и не должен запускаться |

### Безопасный следующий план

1. Создать implementation branch **от актуального GitHub main**, а не от архивного `be66369`.
2. Сначала сверить README/tests/routes в current main и привести их в согласованное состояние.
3. Перенести многостраничный storefront как отдельные Flask routes/templates, используя актуальные DB helpers, 59 опубликованных карточек и подтверждённую медиатеку; сохранить 15 неполных карточек черновиками.
4. Не добавлять фальшивые отзывы/рейтинги/остатки/цены/юридические реквизиты. Все значения с неустановленным источником оставить черновиками.
5. Сохранить `storage.py`, `staff_auth.py`, `commerce_safety.py`, `max_auth.py` текущего main и текущие миграции; любые расширения — отдельными совместимыми миграциями.
6. Реализовать отдельные маршруты и UI для каталога, категорий, товаров, корзины/checkout, аккаунта, отзывов, доставки и клуба. Для каждой страницы — реальные состояния loading/empty/error/success.
7. Затем пройти реальные API/DB security tests, PostgreSQL integration, Playwright E2E и viewport matrix 320–1440 px. Android — отдельный проект и отдельная приёмка.
8. Только после ревью PR и зелёного CI обсуждать merge; production/Render не трогать без разрешения владельца.

**Итоговый статус:** `AUDITED`; тесты архива выполнены частично и не подтверждают production readiness; `CODE_INTEGRATION=BLOCKED` до адаптации. В этот аудит не включались гранты, договоры, внешние аккаунты или секреты.
